# ServersStatus

Единый центр мониторинга Windows Server 2019 / Windows 10 на Raspberry Pi 5 (Linux, ARM64).
Python 3.11+, FastAPI, SQLite, HTML. Обновлённые агенты отправляют отчёты через HTTPS каждые 10 секунд.

## Что реализовано

Вход с хешированием паролей (scrypt), сессии на 8 часов, ограничение попыток входа,
индивидуальные ключи агентов (в базе хранятся только хеши), CPU, RAM, диски,
время работы, Windows-службы, свежесть файлов бэкапов. История хранится 186 дней (не менее 6 календарных месяцев).
Панель показывает карточки серверов, индикаторы CPU/RAM, диски и состояния служб/бэкапов.
Обзор обновляется в фоне каждые 10 секунд. Настройки мониторинга через UI,
уведомления, SQL msdb и управление службами — следующие этапы, они ещё не реализованы.

## Локальная разработка

```sh
python3 -m venv .venv
. .venv/bin/activate
pip install -r requirements.txt
python -m server.cli create-admin admin
python -m server.cli add-agent sql-server-01
# Только для локальной разработки без HTTPS:
STATUS_INSECURE_LOCAL=1 python -m uvicorn server.app:app --host 127.0.0.1 --port 8000
```

Рабочая папка — корень проекта. Ключ из add-agent показывается один раз: перенесите его
в agent/config.json. Не коммитьте этот файл. Повторная регистрация существующего имени
отклоняется. Пароли и ключи не передавайте в аргументах командной строки.

## Raspberry Pi: установка и автоматический запуск

Используйте 64-битный Linux и Python 3.11 или новее. Команды выполняются на Raspberry Pi,
не в облачной среде разработки. Измените путь клонирования, если проект уже скачан.

```sh
sudo apt update
sudo apt install python3-venv git
sudo git clone https://github.com/KrissViktor/ServersStatus.git /opt/ServersStatus
sudo python3 -m venv /opt/ServersStatus/.venv
sudo /opt/ServersStatus/.venv/bin/pip install -r /opt/ServersStatus/requirements.txt
sudo useradd --system --home /var/lib/serversstatus --shell /usr/sbin/nologin serversstatus
sudo install -d -o serversstatus -g serversstatus -m 700 /var/lib/serversstatus
cd /opt/ServersStatus
sudo -u serversstatus env STATUS_DB=/var/lib/serversstatus/status.sqlite3 .venv/bin/python -m server.cli create-admin admin
sudo -u serversstatus env STATUS_DB=/var/lib/serversstatus/status.sqlite3 .venv/bin/python -m server.cli add-agent sql-server-01
sudo cp deploy/serversstatus.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now serversstatus
curl --fail http://127.0.0.1:8000/health
```

Установите Caddy из официального репозитория для вашей ОС по https://caddyserver.com/docs/install.
Создайте DNS A запись домена на статический домашний IP. Замените status.example.com
в deploy/Caddyfile и установите его как /etc/caddy/Caddyfile. Проверьте
`sudo caddy validate --config /etc/caddy/Caddyfile`, затем `sudo systemctl reload caddy`.
Пробросьте TCP 80 и 443 на Raspberry Pi для сертификата и HTTPS. Порт 8000 наружу
не открывайте. Проверьте `/health` через HTTPS с другой сети и вход в панель.
Не задавайте STATUS_INSECURE_LOCAL в рабочем развёртывании.
Для доступа только по IP потребуется отдельная настройка доверенного сертификата;
первое развёртывание рекомендуем делать с доменом.

## Windows-агент

Установите 64-битный Python 3.11/3.12 для всех пользователей в каталог, доступный службе.
Скопируйте проект в `C:\ServersStatus`. В терминале администратора:

```powershell
cd C:\ServersStatus
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r agent\requirements-windows.txt
Copy-Item agent\config.example.json agent\config.json
# Теперь заполните config.json: URL, имя, индивидуальный ключ, службы и папки.
.\.venv\Scripts\python.exe -m agent.client agent\config.json
# После проверки отчёта остановите Ctrl+C и установите службу:
.\.venv\Scripts\python.exe agent\windows_service.py --startup auto install
.\.venv\Scripts\python.exe agent\windows_service.py start
sc.exe failure ServersStatusAgent reset= 86400 actions= restart/10000/restart/30000/restart/60000
```

Ограничьте права на config.json администраторами и учётной записью службы.
По умолчанию служба запускается от LocalSystem. Для сетевых папок настройте отдельную
учётную запись службы с правами чтения и используйте UNC-пути, а не подключённые диски.
Убедитесь, что после перезагрузки Windows отчёты снова появляются в панели.
Установка Windows-службы должна быть проверена на реальной Windows: Linux этого не проверяет.

Для бэкапов настройте отдельную папку/правило для каждой базы: иначе свежий файл одной
базы может скрыть отсутствие копии другой. `observing` — размер/mtime ещё не подтверждены
двумя опросами; `fresh` — файл стабилен и свеж; `stale` — просрочен; `missing` — файлов нет.
Стабильность файла не подтверждает целостность SQL-бэкапа или завершение копирования
при длительной паузе. Для надёжного контроля нужны журнал переноса и тест восстановления.

## Windows без установки Python: EXE

GitHub Actions → **Build Windows agent** → последний успешный запуск →
Artifacts → **ServersStatus-Windows-x64**. Распакуйте архив и запустите
`ServersStatusSetup.exe` от администратора. Введите URL панели, зарегистрированное
имя и ключ агента. Установщик сначала отправит проверочный отчёт, затем установит
службу с автоматическим запуском. Первый отчёт проверки содержит нулевые показатели;
настоящие показатели придут от службы. Отдельный Python не нужен.

Сборка выполняется Windows runner GitHub после изменений агента. Перед упаковкой
установщика CI проверяет регистрацию, запуск и остановку собранной службы.
Это не заменяет проверку на Windows Server 2019 / Windows 10 и после перезагрузки.
EXE пока без цифровой подписи издателя.

Расположение файлов:
- `%ProgramFiles%\ServersStatus\ServersStatusService.exe` — исполняемый файл службы;
- `%ProgramData%\ServersStatus\config.json` — конфигурация и ключ;
- `%ProgramData%\ServersStatus\agent.log` — журнал ошибок (с ротацией).

Каталог данных ограничен SYSTEM и администраторами. Для первого подключения
используется LocalSystem; доступ к сетевым бэкапам настраивается отдельно.

Для удаления службы в PowerShell администратора:

```powershell
& "$env:ProgramFiles\ServersStatus\ServersStatusService.exe" stop
# Дождитесь состояния Stopped:
Get-Service ServersStatusAgent
& "$env:ProgramFiles\ServersStatus\ServersStatusService.exe" remove
```

Для обновления удалять службу не нужно: запустите новый ServersStatusSetup.exe
и нажмите «Обновить установленный агент» без ввода ключа. Настройки сохраняются, правила бэкапов
и служб установщик не сбрасывает. Полное удаление каталогов выполняйте только
после удаления службы; в каталоге данных хранится ключ подключения.

## Управление агентами в панели

После входа откройте «Управление агентами». Создайте идентификатор из латинских
букв, цифр, дефисов и подчёркиваний (до 64 символов). Ключ показывается только в
ответе на создание; в базе хранится его хеш. Запишите имя и ключ в EXE-установщик.
Существующие агенты после обновления сервера продолжают работать.

Перевыпуск сразу отключает старый ключ и сохраняет историю. На Windows измените
`token` в `%ProgramData%\ServersStatus\config.json` от администратора, затем:

```powershell
Restart-Service ServersStatusAgent
```

Если агент установлен старым способом из Python, конфигурация находится в
`C:\ServersStatus\agent\config.json`.
Удаление требует ввести точное имя и удаляет регистрацию вместе с историей;
саму Windows-службу нужно остановить/удалить отдельно. Страница управления не
обновляется автоматически, чтобы не прерывать ввод и сохранение ключа.


## История CPU и RAM

В карточке сервера нажмите «История CPU / RAM». Периоды: час, 6 часов, сутки,
неделя и 30 дней. Используются уже сохранённые отчёты, Windows-агент обновлять
не требуется. Страница доступна после входа и обновляется каждые 30 секунд.
Время на графиках — московское (МСК). Наведение на точку показывает её среднее,
пиковое значение, интервал и количество отчётов. Для RAM также показываются
исторические объёмы занятой памяти; в сводных «Среднее RAM» и «Пик RAM»
объём указан в Мб/Гб автоматически. Если старые отчёты не содержали объёма,
он отмечается как недоступный.

Нажмите точку графика CPU/RAM, сети или дисковых операций — поверх страницы
откроется полноэкранный график исходных отчётов без усреднения. Он включает
отчёты выбранной точки (до 900) и ближайшие измерения, если их меньше 30.
«Отдалить ×3» увеличивает число отчётов: например, 30 → 90 → 270 → 810 → 900.
«Приблизить» и колесо мыши меняют масштаб; перетаскивание и стрелки перемещают
окно по времени. Закрытие — кнопкой или Escape. Мини-графики карточек тоже
открывают это окно. API требует обычного входа и ограничивает ответ 900
отчётами; никаких дополнительных зависимостей или обновлений агента не нужно.

Данные группируются по интервалам 1, 1, 5, 30 и 60 минут соответственно.
Сводные средние учитывают количество отчётов, пики вычисляются по исходным
значениям. Это максимум полученных измерений, а не всех мгновенных нагрузок.
Отсутствие отчётов не заменяется нулями. Разрывы свыше 3 минут не соединяются;
агрегированные интервалы с пропусками отображаются отдельными точками.
Хранение — 186 дней (не менее 6 календарных месяцев). Если агент подключён недавно, предыдущих данных не будет.
Графики SVG встроены в страницу и не требуют внешних CDN или новых зависимостей.


## Готовые правила для WIN-CU629F0N7II

Универсальный архив `ServersStatus-Windows-x64` содержит EXE и общий скрипт
обновления. Отдельный архив `Backup-rules-WIN-CU629F0N7II` содержит
`Update-BackupAgent.ps1` и `backups.WIN-CU629F0N7II.json`. Для установки этих правил
распакуйте оба архива в один каталог.
Скрипт запускается только на этом компьютере и заменяет четыре правила бэкапов,
сохраняя URL, имя, ключ, службы и другие параметры. Перед заменой сохраняются
резервные копии EXE и config.json в их текущих защищённых каталогах; при ошибке
обновления скрипт пытается восстановить прежние файлы и запустить службу.

Распакуйте архив в `C:\ServersStatusUpdate`, затем в PowerShell администратора:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File C:\ServersStatusUpdate\Update-BackupAgent.ps1
```

Правила: ERP и Бух ERP; ежедневные каталоги `D:\backup\erp\daily` и
`D:\backup\erp_buh\daily`; ежемесячные `D:\backup\erp\monthly` и
`D:\backup\erp_buh\monthly` с рекурсивным поиском. Выбор копии и свежесть —
по дате в имени `_backup_YYYY_MM_DD_HHMMSS_`, не по времени переноса.
Шаблоны имён отдельно для ERP и ERP_INTEK. Для ежедневных допустимый возраст 30 ч.
Для месячных требуется файл за 1-е число текущего месяца после 12:00 2-го числа;
до этого принимается копия за 1-е число предыдущего месяца. Все расчёты расписания
используют локальное время Windows-компьютера: проверьте его часовой пояс и часы.

Два опроса подтверждают неизменность размера и mtime; это не проверка целостности
бэкапа. Нет файла — `missing`; ошибка доступа/отсутствующий каталог — `error`;
нулевой размер — `empty`; дата более чем на 5 минут в будущем — `future`.
Скрипт Windows-обновления требует проверки на реальном компьютере; Linux проверяет
логику расписаний, но не замену работающего Windows-сервиса.


## Красные предупреждения о бэкапах

В начале главной панели появляется большой красный блок с сервером, правилом и
причинами: нет файлов, ежедневная копия старше 30 часов, файл меньше 1 Гб,
недоступная папка или дата из будущего. Причины также дублируются в карточке.
Порог размера — 1 073 741 824 байта (1024³); ровно этот размер допустим.
Порог возраста — строго более 30 часов. Проверка размера относится к ежедневным
и месячным файлам и не доказывает целостность файла, прошедшего порог.

Для агентов, уже передающих бэкапы, достаточно обновить веб-сервер: панель сама
оценивает размер и возраст, независимо от старого порога 26 часов в агенте.
При потере связи возраст увеличивается от времени последнего отчёта и явно
показывается, что состояние основано на устаревших данных. Новые правила агента
также используют пороги 30 часов и 1 Гб. Файл, который ещё переносится и меньше
порога, тоже вызовет уведомление; оно уйдёт, когда придёт подходящий свежий файл.


## Расширенные показатели Windows

Новый агент передаёт версию/редакцию ОС, архитектуру, описание CPU, физические
ядра и логические потоки, общий и доступный объём RAM, файловую систему томов.
Сетевые интерфейсы: IP, состояние, скорость линка (Мбит/с), приём и передача
(байт/с). Диски: чтение/запись (байт/с), число операций IOPS по устройствам Windows.
Скорости вычисляются по разнице счётчиков за одну секунду измерения CPU; это
снимок нагрузки перед отчётом, а не среднее за минуту. Новые/сброшенные счётчики
не подменяются нулевой нагрузкой. При недоступности счётчиков панель сообщает об этом.

Сначала обновите Raspberry Pi. Затем скачайте последнюю успешную Windows-сборку
из GitHub Actions и распакуйте в `C:\ServersStatusUpdate` на каждом компьютере.
В PowerShell администратора выполните:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File C:\ServersStatusUpdate\Update-Agent.ps1
```

Этот общий скрипт меняет только EXE, сохраняет резервную копию, перезапускает службу
и пытается откатить её при ошибке. Ключ, имя, службы и правила бэкапов не меняются.
Скрипт Update-BackupAgent.ps1 предназначен для отдельной установки четырёх правил
конкретного компьютера и для обычного обновления метрик не нужен.
Старые агенты совместимы с сервером, но расширенных блоков не заполняют.
Соответствие физических устройств буквам томов не определяется, SMART и температура
пока не собираются. Доступность I/O-счётчиков зависит от конфигурации Windows.


## Универсальное обновление через EXE

`ServersStatusSetup.exe` подходит для всех поддерживаемых компьютеров Windows x64,
ограничений по hostname у него нет. Скачайте последний успешный артефакт
**ServersStatus-Windows-x64**, распакуйте и запустите EXE от администратора.
Нажмите **«Обновить установленный агент»**. Имя/ключ вводить повторно не нужно.
Установщик остановит службу, сохранит копию старого EXE, заменит бинарник и проверит
запуск. При сбое попытается вернуть старый EXE и запустить службу. config.json,
индивидуальный ключ и правила бэкапов этот путь обновления не меняет.
Первая установка по-прежнему требует заполнить поля и нажать «Установить».

Файл `ServersStatusService.exe` — сам сервис, не графический установщик.
`Update-BackupAgent.ps1` — только настройка правил конкретного хранилища; на других
компьютерах он намеренно отказывается работать. Для обычного обновления используйте
EXE с кнопкой обновления либо общий `Update-Agent.ps1`.

## Настройки мониторинга через веб-панель

Обновите веб-сервер, затем нужные Windows-агенты через новый универсальный
ServersStatusSetup.exe → «Обновить установленный агент».
Откройте «Управление агентами» → «Настройки бэкапов и служб» у нужного компьютера.

Укажите системные имена служб по одному на строку (например MSSQLSERVER).
Для каждой папки задайте название, путь на Windows-компьютере, маску файла,
ежедневное/месячное расписание, вложенный поиск, чтение даты SQL из имени,
максимальный возраст, месячную отсрочку и минимальный размер в Гб (1024³ байт).
Пустой путь или удаление строки убирают правило; пустой список служб отключает
их мониторинг. Перед первым сохранением проверьте поля, предзаполненные по отчёту.
По умолчанию возраст — 30 ч, минимальный размер — 1 Гб, месячная отсрочка — 36 ч.

Нажмите «Сохранить и передать агенту». Статус меняется с «Ожидает получения» на
«Применено агентом» после следующего отчёта с новой версией. Обычно нужно 1–2
минуты. Страница не обновляется автоматически, чтобы не прерывать редактирование.
Старый EXE не получает настройки — панель предлагает его обновить.

Сервер возвращает правила в ответе на авторизованный отчёт; агент применяет их
со следующего цикла. Последние полученные правила сохраняются рядом с локальным
config.json в config.json.remote.json и используются после перезапуска/при потере
связи. Сам config.json и ключ остаются неизменными. До первого сохранения настроек
в панели работают локальные правила. Кнопка возврата к локальному файлу требует
подтверждения; агент переключится после следующего успешного контакта с сервером.

Передаются только настройки мониторинга папок и служб, без команд управления.
Красные уведомления учитывают выбранные возраст и размер из отчёта агента.
Удаление агента удаляет также его серверные настройки.

Настройка бота, защищённого файла с токеном, тестовой отправки и фонового таймера:
[deploy/TELEGRAM.md](deploy/TELEGRAM.md). Windows-агенты обновлять не нужно.
Проблемы бэкапов и связи с агентами отправляются один раз до восстановления;
состояние рассылки сохраняется в SQLite. Реальная отправка требует токена бота,
ID чата и доступа Raspberry Pi к api.telegram.org.

Если Telegram доступен через Hysteria2, можно направить только уведомления через
локальный SOCKS5: [инструкция для Raspberry Pi](deploy/HYSTERIA2.md).

## Обзор серверов, поиск и понятные названия

Главная страница показывает компактные карточки CPU/RAM, дисков и основных проблем.
Поиск работает по отображаемому названию, hostname и ID агента без учёта регистра.
Фильтры: все серверы, есть проблемы, нет связи. Сохранённые параметры поиска
остаются в адресе страницы при автообновлении. Сводка и красный блок бэкапов всегда
охватывают все серверы, даже если карточки отфильтрованы.

В «Есть проблемы» входят потеря связи, CPU/RAM от 95%, диски от 85%, ошибки бэкапов
и неработающие контролируемые службы. Агент без первого отчёта обозначается как
ожидающий данных, а не потерявший связь.

Нажмите название или «Открыть сервер», чтобы увидеть полные сведения, сеть,
дисковые операции, службы, бэкапы и исходный отчёт. Внизу этой страницы можно
сохранить понятное название, например «SQL — ERP»; оно не меняет Windows hostname,
ID и ключ агента. Очистка поля возвращает техническое имя.
Обзор и подробные показатели обновляются в фоне каждые 10 секунд. Поле названия
находится вне обновляемого блока, поэтому ввод сохраняется.
Windows-агенты обновлять не требуется.

Поиск обновляет карточки во время ввода (задержка 180 мс), выбор статуса — сразу.
Страница не перезагружается, устаревшие ответы поиска не заменяют новые.
Проблемные карточки выделены рыжим фоном. При отключённом JavaScript доступна
обычная кнопка поиска.

Обзор и подробности обновляются каждые 10 секунд, исторические графики — каждые
30 секунд, без перезагрузки документа. Поле поиска, фокус и прокрутка сохраняются; во время
редактирования поиска фоновый опрос обзора пропускается. Счётчики и предупреждения
обновляются вместе с карточками. Единицы объёма отображаются как Кб, Мб, Гб, Тб
и Пб; расчёт по 1024 не изменён.

## Частота данных и размер истории

Новый агент после успешного контакта получает от сервера интервал 10 секунд,
даже если в старом локальном config.json осталось 60. Время сбора входит в
интервал, а не добавляется к нему. Для перехода Windows нужно обновить EXE.
Свежий снимок каждого агента хранится отдельно в latest_reports; reports
сохраняет каждый полученный отчёт без прореживания. Панель/события/бот
читают свежие данные; графики и прогноз агрегируют полную историю только
для отображения, исходные записи остаются в базе 186 дней.

## Telegram-бот с кнопками

Статус, Отчет за 24 часа, RDP, Предупреждения, Панель и Помощь. Команды доступны
только настроенному чату и отвечают по запросу в любое время; авторассылка
сохраняет дневное расписание. Постоянная systemd-служба с автоперезапуском,

монтирования и snap не вызывают предупреждений; правило применяется также к
старым снимкам в панели и Telegram.

Кнопка Telegram «Бэкап» (/backup) показывает свежесть, имя и размер файла,
дату копии и возраст в часах/минутах/секундах. Рабочие и отключённые состояния
в Telegram-сводках отмечены зелёными и красными кружками.


## Полная история за шесть месяцев

Сохраняется каждый принятый отчёт, в том числе поступающий каждые 10 секунд.
Промежуточные записи больше не отбрасываются. Срок хранения — 186 дней, что
покрывает любые 6 календарных месяцев; более старые данные удаляются пакетами
до 10 000 строк с паузами. Последний снимок каждого агента хранится отдельно.
Ограничение числа точек на графике не является удалением исходных измерений:
для точки считаются средние и пики по всем сохранённым отчётам.

Для очистки добавлен временной индекс, для CPU/RAM — индекс метрик. Сеть и
дисковые операции читаются одним проходом на группу, вместо отдельного прохода
для каждого поля. Периоды графиков пока сохраняются прежними, до 30 дней;
более старая полная история также сохраняется в базе.

Изменение применяется после обновления Raspberry Pi; агенты менять не требуется.
Прежние удалённые/не сохранённые промежуточные данные восстановить невозможно.
Объём базы теперь растёт примерно в 6 раз быстрее, чем при минутной истории,
и зависит от размеров отчётов и числа серверов. Индексы требуют дополнительного
места. При первом запуске на существующей базе построение индексов может занять
время; не прерывайте процесс, проверьте журнал при задержке запуска.

CPU и RAM в карточках и подробностях представлены графиками в стиле диспетчера
задач: сетка 0–100%, линия и заливка за последние 5 минут. CPU — синий, RAM —
фиолетовый. Используются реальные сохранённые измерения; при нехватке истории
прошлые значения не дорисовываются. Проценты, ГГц и занято/всего RAM сохранены.
Обновление остаётся фоновым каждые 10 секунд; агенты менять не требуется.

## Флажки агентов и компактное управление

В «Администрирование» → «Управление агентами» карточки расположены сеткой.
Сверху видны имя из обзора серверов, постоянный ID агента и два флажка:

- **Важный** — автоматические уведомления Telegram о проблемах и
  восстановлении, а также общий баннер ошибок бэкапов. Снятие флажка очищает
  ожидающие предупреждения этого агента без сообщения о восстановлении.
- **Активный** — карточка в основном списке обзора. Остальные серверы находятся
  ниже под спойлером «Не активные». При поиске/фильтре этот спойлер автоматически
  раскрывается для найденных серверов; при фоновом обновлении сохраняет выбор.

Оба флага независимы и сохраняются сразу. По умолчанию для существующих и новых
агентов включены оба. Сбор метрик, журнал и отчёты доступны для всех серверов.
Флаг важности управляет предупреждениями; суточная сводка и ручные запросы боту
остаются общими отчётами.

Нажмите имя агента, чтобы раскрыть изменение имени в панели, ссылку на настройки
мониторинга и операции с ключом/удалением. Флажки остаются видимыми и доступными.
Форма добавления компьютера также свёрнута до нажатия. Обновление агентов
для этих настроек не требуется.


## Снимки состояния и переход к экстремумам

В подробном графике значение и время видны в подсказке у указателя. Нажатие
выбирает исходный отчёт; внизу показано его время. Кнопка «Снимок» открывает
состояние сервера на тот момент: CPU/RAM, диски, службы, бэкапы, систему и RDP.
Снимок доступен для любого сохранённого исходного отчёта, без команд управления.

В истории «Пик CPU», «Минимум CPU», «Пик RAM», «Минимум RAM» открывают подробный
график вокруг точного исходного экстремума выбранного периода. Средние значения
остаются справочными. В подробном окне кнопки «Минимум»/«Максимум» выбирают
соответствующий исходный отчёт текущего окна (до 900 измерений).

Для объяснения нагрузки снимок показывает все полученные процессы в едином
диспетчере задач: вкладки «Процессы» / «Службы», отдельные имя и PID, прокрутка,
поиск, фильтр состояния и сортировка по колонкам без подтверждения. Тот же блок
есть в текущем отчёте. Все доступные поля раскрываются в «Сведения».
Полный список процессов хранится сжатым, с привязкой к ID/времени отчёта,
и удаляется вместе с ним через 186 дней. Это увеличивает архив по сравнению
с прежним сохранением топа. Поддерживающие привязку агенты менять не требуется.

Полные службы сохраняются сжатыми ревизиями при изменении списка. В снимке
выбирается только ревизия, полученная до выбранного отчёта, и показывается её
время: сбор служб происходит раз в минуту, отдельно от процессов/метрик.
Старые снимки, где был сохранён только топ процессов или не было истории
служб, явно отмечаются; недостающие данные восстановить нельзя.

В старых отчётах процессы не сохранялись. Для них показывается отсутствие
истории; текущие процессы к старому моменту не приписываются. Ошибки чтения
процессов агентом и сокращённые списки также явно отмечаются.
