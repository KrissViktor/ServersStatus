# Raspberry Pi и обновления агентов из панели

## 1. Обновление панели и мониторинг Raspberry Pi

На Raspberry Pi:

    cd /opt/ServersStatus
    sudo git pull --ff-only origin main
    sudo cp deploy/serversstatus-host-monitor.service /etc/systemd/system/
    sudo systemctl daemon-reload
    sudo systemctl restart serversstatus
    sudo systemctl enable --now serversstatus-host-monitor
    sudo systemctl status serversstatus-host-monitor --no-pager

Служба работает от пользователя serversstatus и использует существующую базу.
Каждые 10 секунд сохраняет CPU, ОЗУ, корневой диск, сеть, дисковые операции,
время работы, состояние установленных служб панели и бота. Температура читается
из sysfs; при отсутствии датчика показывается «датчик недоступен».
Размер базы включает SQLite WAL/SHM. История хранится по общей настраиваемой политике (по умолчанию 186 дней).
В меню появятся «Raspberry Pi» и «Обновления». Raspberry Pi также видна в общем
списке, графиках и Telegram. Не создавайте вручную агент с ID raspi-portal:
этот ID резервирует локальная служба. При конфликте она завершится с ошибкой.

Проверка журнала:

    sudo journalctl -u serversstatus-host-monitor -n 50 --no-pager

Raspberry Pi не обновляется как удалённый агент: её код обновляется вместе с порталом.
Если Pi полностью выключится, её бот тоже остановится: для оповещения о полном
отказе Pi нужен отдельный внешний монитор.

## 2. Один раз подготовить агенты

Старые версии не умеют устанавливать обновления. Поэтому сначала обновите их
обычным способом. После этого последующие совместимые версии можно ставить из панели.

### Windows Server 2019 / Windows 10 x64

В GitHub Actions откройте успешный запуск **Build Windows agent** после этого
изменения, скачайте **ServersStatus-Windows-x64**. Распакуйте на Windows в
C:\ServersStatusUpdate. В PowerShell от администратора:

    powershell.exe -NoProfile -ExecutionPolicy Bypass -File C:\ServersStatusUpdate\Update-Agent.ps1

Используйте универсальный Update-Agent.ps1 на всех компьютерах.
Update-BackupAgent.ps1 предназначен только для правил бэкапов на WIN-CU629F0N7II.
Установленная служба должна находиться в стандартном каталоге
C:\Program Files\ServersStatus\ServersStatusService.exe. Конфигурация остаётся
в C:\ProgramData\ServersStatus\config.json. Агент должен работать как LocalSystem,
как его устанавливает штатный установщик.

После нового отчёта в «Обновлениях» появится версия и возможность обновления.
SHA256SUMS.txt и VERSION.txt из того же артефакта понадобятся для размещения пакета на Pi.
Сам файл для удалённого обновления — **ServersStatusService.exe**, не Setup.exe.

### Linux (включая CentOS Stream 9)

На Linux-сервере под root обновите исходный checkout (до первого удалённого обновления):

    cd /opt/serversstatus-agent/current
    git pull --ff-only origin main
    /opt/serversstatus-agent/.venv/bin/python -m pip install -r agent/requirements-linux.txt
    install -d -o root -g root -m 755 /etc/serversstatus-agent
    install -o root -g root -m 600 /var/lib/serversstatus-agent/config.json /etc/serversstatus-agent/update.json
    cp deploy/serversstatus-agent-updater.service deploy/serversstatus-agent-updater.timer /etc/systemd/system/
    systemctl daemon-reload
    systemctl restart serversstatus-agent
    systemctl enable --now serversstatus-agent-updater.timer

Это отдельный root-updater. Обычный агент остаётся непривилегированным.
Код в /opt/serversstatus-agent и root-конфигурация не должны быть доступны на запись
пользователю serversstatus-agent. Не меняйте владельца этих каталогов на агента.
update.json содержит копию адреса панели, имени и ключа. После перевыпуска ключа
обновляйте обе конфигурации, сохраняя update.json root:root 600.
Таймер проверяет задания раз в 30 секунд.

После удалённой установки current становится ссылкой на каталог releases.
Для дальнейших обновлений используйте панель; git pull внутри этого каталога
уже не применяется. Смена зависимостей Python требует ручного обновления venv:
root-updater отклоняет пакет, если requirements-linux.txt отличается.

## 3. Обновления прямо из GitHub Releases (основной способ)

После обновления панели выполните:

    cd /opt/ServersStatus
    sudo git pull --ff-only origin main
    sudo systemctl restart serversstatus

Дождитесь успешных сборок **Build Windows agent** и **Test Linux agent** в GitHub
Actions. На main они публикуют публичные Releases с программой агента и JSON
манифестом (платформа, версия commit SHA, размер, SHA256 и адрес файла).
Windows и Linux используют отдельные релизы agent-windows-VERSION и
agent-linux-VERSION. Маленькие файлы update-windows.json / update-linux.json
в релизе agents-stable указывают на последние успешные сборки.

В панели откройте **Обновления → Проверить GitHub**, затем выберите версию у
нужного сервера и нажмите **Обновить агент**. Переносить EXE/архив на Pi и
запускать команду регистрации пакета больше не требуется. Установка остаётся
по вашей команде, а не при каждом новом коммите без предупреждения.

Новый агент скачивает бинарник/архив напрямую с публичного GitHub по HTTPS,
проверяет размер и SHA256 и использует прежний механизм установки/отката.
Его ключ панели на GitHub не передаётся. Разрешены только Releases этого
репозитория и HTTPS-переадресация на домены GitHub release assets.
GitHub-токен ни на Pi, ни на Windows/Linux-серверах не нужен.

Агенты, у которых уже есть remote_update_v1, умеют получить первое обновление
через прежний endpoint панели: Pi передаст им назначенный файл потоком из
GitHub без ручного размещения и без хранения EXE/архива на Pi. После установки
новой версии дальнейшие скачивания выполняются напрямую с GitHub. Совсем
старым агентам без поддержки удалённой установки всё ещё нужен ручной шаг
из раздела 2. Служба root-updater на Linux остаётся необходимой.

Для проверки каталога должны быть опубликованы манифесты обеих платформ.
Пока первые сборки не закончились, либо GitHub недоступен, проверка покажет
ошибку и сохранит прежний каталог. На серверах нужен исходящий HTTPS-доступ
к github.com и release-assets.githubusercontent.com; возможен также переход
на objects.githubusercontent.com. При ошибке скачивания старая служба не
заменяется. Результат установки подтверждается телеметрией, как раньше.

Повторный запуск CI использует уже опубликованный пакет той же версии;
исполняемые файлы в версионном релизе не перезаписываются. Обновляется только
указатель канала. Публикация использует штатный GITHUB_TOKEN с contents:write
в workflow основного репозитория. Если GitHub ограничил запись workflow,
проверьте ошибку шага Publish public GitHub release и настройки Actions.
Пакеты и суммы берутся из вашего публичного репозитория; SHA256 проверяет
целостность, доверие к коду определяется доступом к самому репозиторию.

## 4. Разместить локальный пакет на Raspberry Pi (запасной способ)

Пакеты заранее скачивает администратор из успешной сборки GitHub Actions и
передаёт на Pi, например через SCP. Панель не принимает произвольные URL и
не загружает исполняемые файлы через веб-форму. Каталог пакетов root-owned,
веб-служба может только читать его. По HTTPS пакет получают только агенты,
которым администратор назначил именно это обновление.

Для Windows загрузите на Pi ServersStatusService.exe, VERSION.txt и SHA256SUMS.txt
из одного артефакта. Для Linux — ServersStatus-Linux.tar.gz и соответствующие файлы
из **ServersStatus-Linux-Python311**. VERSION.txt содержит 12 символов commit SHA.
Сверьте контрольную сумму с артефактом. Выполните на Pi, подставляя реальные
версию, путь и SHA256 (64 шестнадцатеричных символа):

    cd /opt/ServersStatus
    sudo env STATUS_DB=/var/lib/serversstatus/status.sqlite3 .venv/bin/python -m server.updates windows-x64 VERSION /home/admin/ServersStatusService.exe SHA256

Для Linux:

    sudo env STATUS_DB=/var/lib/serversstatus/status.sqlite3 .venv/bin/python -m server.updates linux-source VERSION /home/admin/ServersStatus-Linux.tar.gz SHA256

Не меняйте существующий STATUS_DB, если у вас используется другой путь.
SHA256 проверяется перед регистрацией. Повторная регистрация одинакового файла
не нужна. Храните только доверенные сборки своего репозитория: этот код выполняется
с правами службы агента (LocalSystem на Windows, root-helper при установке Linux).

Откройте **Обновления**, выберите подходящую версию у нужного сервера и нажмите
**Обновить агент**. Устанавливайте сначала на одном сервере. Будет короткий перерыв
в отчётах. Windows получает задание примерно за 10 секунд, Linux — до 30 секунд.
Обновляется программа агента; Windows/Linux и приложения 1C/SQL не обновляются.

Состояния: «В очереди» → «Установка» → «Установлено». Последнее появляется только
после отчёта с ожидаемой версией и платформой. Через 15 минут без подтверждения —
«Ошибка», а не ложный успех. Обновите страницу «Обновления», чтобы увидеть результат.

При ошибке запуска helper пытается вернуть предыдущую версию. Windows сохраняет
EXE рядом со службой с расширением .job-ID.previous. Linux сохраняет previous-ID
в /opt/serversstatus-agent. Старые версии автоматически не удаляются: после проверки
можно удалить ненужные резервные копии вручную. При отключении питания посреди
замены или ошибке восстановления проверьте службу локально перед повторной попыткой.

Linux-журнал:

    journalctl -u serversstatus-agent-updater -n 50 --no-pager
    systemctl status serversstatus-agent --no-pager

На Windows проверьте службу ServersStatusAgent и журнал агента в
C:\ProgramData\ServersStatus. Настройки мониторинга и ключи при штатной установке
не перезаписываются.

## Восстановление Windows после ошибки замены EXE

Старый встроенный PowerShell-помощник мог пытаться заменить EXE сразу после
SCM Stopped, пока родительский процесс PyInstaller ещё удерживал файл.
Исправленный помощник ждёт завершения процессов/освобождения файла, повторяет
копирование и записывает этап ошибки в update.log. Это возможная причина общей
ошибки Windows; при ошибке скачивания или запуска нужны соответствующие журналы.
Новая панель показывает отдельные сообщения download/verify/stop/wait_exit/
backup/replace/start/health и результат восстановления, не раскрывая токены.

Сначала обновите код панели и дождитесь успешной новой Windows-сборки:

    cd /opt/ServersStatus
    sudo git pull --ff-only origin main
    sudo systemctl restart serversstatus

Если обновление через панель продолжает падать, в старом EXE остался прежний
помощник. Ему нужен один локальный переход на исправленную версию. На каждом
таком Windows-сервере в PowerShell **от администратора**:

    Invoke-WebRequest -UseBasicParsing -Uri 'https://raw.githubusercontent.com/KrissViktor/ServersStatus/main/agent/Repair-WindowsAgent.ps1' -OutFile "$env:ProgramData\ServersStatus\Repair-WindowsAgent.ps1"
    powershell.exe -NoProfile -ExecutionPolicy Bypass -File "$env:ProgramData\ServersStatus\Repair-WindowsAgent.ps1"

Скрипт скачивает только публичную Windows-сборку вашего репозитория с
updater_protocol=2, проверяет размер/SHA256, использует исправленный помощник,
сохраняет резервный EXE и перезапускает только службу агента. Если новая сборка
ещё не опубликована, скрипт завершится до изменения установленной службы.
Конфигурация, имя, ключ и правила бэкапов сохраняются; ОС не перезагружается.
Код помощника берётся из main вашего доверенного репозитория по HTTPS.
После перехода следующие обновления можно снова назначать из панели.

Локальный журнал восстановления:

    Get-ChildItem "$env:ProgramData\ServersStatus\repair-*\update.log" | Sort-Object LastWriteTime -Descending | Select-Object -First 1 | Get-Content

Новые обновления через портал пишут журнал в
C:\ProgramData\ServersStatus\updates\ID_ЗАДАНИЯ\update.log. Старые версии такого
журнала не создавали. Журнал agent.log дополнительно фиксирует этап ошибки
скачивания/подготовки без текста исключения с URL или ключом.

Запасной способ: скачать полный новый Windows artifact из GitHub Actions,
распаковать EXE, apply_update.ps1 и Update-Agent.ps1 в один каталог и запустить
Update-Agent.ps1 от администратора. Не смешивайте файлы разных сборок.

Если EXE скачан, но update.log отсутствует: проверьте состав каталога задания
(должны быть apply_update.ps1 и manifest.json) и agent.log. В новом launcher
дополнительно сохраняется helper-launch.log со stdout/stderr PowerShell, а ранний
ненулевой exit code отображается как helper_startup вместо ожидания 15 минут.
Сам helper начинает update.log до чтения manifest/config; ошибка их разбора
записывается без исходного JSON, чтобы не раскрывать ключ.

## Короткий список версий и журнал

В карточке выделена установленная версия. Выбор содержит максимум два варианта:
- (New) — последняя доступная версия новее установленной;
- (Older) — ближайшая доступная версия старше установленной, для отката.

Рядом указана дата dd.mm.yyyy hh:mm по Москве. Новые манифесты содержат дату
сборки и коммита. Для старых сборок панель использует дату коммита из локального
Git-репозитория, если она доступна; неизвестную дату не выдумывает. Сравнение
выполняется по времени исходного коммита, а не по алфавиту SHA. Для старых ручных
версий без дат используется порядок регистрации в каталоге.

Старые пакеты остаются доступными для уже назначенных заданий и истории;
длинный список убран из выбора. Канал GitHub содержит последнюю сборку и один
предыдущий манифест: после «Проверить GitHub» даже новая панель получает вариант
отката без импорта всех исторических релизов. Если предыдущая версия ещё не
попадала в канал/каталог, она появится после публикации и проверки новых сборок.

История показывает 10 последних заданий в блоке с прокруткой высотой до 300 пикселей. Все записи изначально свёрнуты; подробности открываются по нажатию.
Внутри — исходная и целевая версии, время (МСК), этапы и результат. Старые записи,
для которых промежуточных этапов не сохранялось, показывают создание и последний
известный результат. Новые задания сохраняют скачивание/проверку, ожидание
подтверждения и итог; одинаковые повторные сообщения не дублируются.

Экран обновляется каждые 10 секунд, сохраняя выбранную версию и раскрытые записи.
Когда текущая версия агента меняется, галочка разрешения установки снимается:
переход на следующую версию или откат требует нового подтверждения.

Положение прокрутки истории обновлений сохраняется при автоматическом обновлении.

Прокрутка истории работает по фокусу: без нажатия колёсико над блоком листает
страницу. Нажмите внутри истории (или перейдите в неё клавишей Tab), чтобы
листать записи. При уходе указателя из блока или переводе фокуса наружу снова
листается страница. Заголовок истории закреплён внутри блока. Автообновление
сохраняет позицию прокрутки и раскрытые записи.

## Отмена заданий обновления

На странице «Обновление агентов» у ожидающего задания есть «Отменить задание #…».
Вверху — «Отменить все ожидающие обновления». Отмена доступна администраторам,
защищена CSRF и сохраняется в истории со статусом «Отменено». Повторная отмена
того же отменённого задания безопасна. История не удаляется.

Отменяется только queued — до принятия агентом. Отмена и подтверждение running
сериализованы транзакцией SQLite: победившая операция определяет результат.
Отменённое задание больше не выдаётся и не позволяет скачивать пакет с портала;
позднее подтверждение запуска получает HTTP 409 (существующие агенты прерывают
запуск при ошибке этого запроса). Текущий агентский протокол менять не требуется.
Уже подтверждённую установку/скачивание forcibly не прерываем: кнопки нет,
прямая попытка отмены получает 409, массовая отмена такие задания пропускает.
Отмена не откатывает уже установленное ПО и не удаляет драйверы на сервере.

Для включения функции обновите код портала и перезапустите serversstatus:
это краткий перерыв работы сайта, без перезагрузки Raspi/Windows-серверов.
Обновлять или перезапускать агентов ради функции отмены не требуется.
