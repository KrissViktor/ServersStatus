# Все службы Windows/Linux и процессы в снимках

## Обновление

На Raspberry Pi:

```bash
cd /opt/ServersStatus
sudo git pull --ff-only origin main
sudo systemctl restart serversstatus
sudo systemctl try-restart serversstatus-host-monitor
```

Обновите Windows/Linux-агенты из панели. Локальный сборщик Raspberry Pi
использует код репозитория, поэтому ему нужен указанный restart.

На странице сервера откройте «Диспетчер задач»: вкладки «Процессы» и «Службы».
Показаны все полученные строки в прокручиваемой таблице с закреплённой шапкой.
Имя и PID разделены. Поиск, фильтр состояния, выбор сортировки и нажатие на
заголовок столбца применяются сразу. В каждой строке «Сведения» раскрывает
доступные поля. Этот же компонент используется в снимке из графика.
Полный список служб собирается фоном раз в минуту. Закрытая вкладка/блок
не опрашивается браузером; поиск и раскрытия сохраняются при обновлении.

- 🟢 Работает.
- 🔴 Остановлена или ошибка (подпись различает эти состояния).
- 🟡 На паузе.
- 🟠 Запускается, останавливается, возобновляется или перезагружается.
- ⚪ Недоступна/неизвестна.

Состояние выполнения и автозапуск показаны отдельно. Например, выключенный
автозапуск не означает, что служба сейчас остановлена.

Windows: имена/описания, состояние, PID, учётная запись, тип запуска, бинарный
путь и доступные параметры SCM (зависимости, группа загрузки, тип и обработка
ошибок). Linux: объединены установленные и загруженные .service units,
показываются ActiveState/SubState, автозапуск, PID, пользователь/группа,
ExecStart/ExecStop, файл/переопределения, зависимости, перезапуски, результат,
времена и доступные ресурсные свойства systemd. Объём данных ограничен 5000
службами/примерно 1,9 Мб; частичное чтение и сокращение явно отмечаются.

Это отдельная полная инвентаризация: обычные остановленные службы не создают
новых предупреждений. Уведомления и исторические отчёты продолжают использовать
настроенный список контролируемых служб. Команд запуска/остановки здесь нет.
Доступ к текущему списку есть у всех вошедших пользователей, согласно ролям.

## Почему в старом снимке нет процессов

Снимок показывает процессы только если для этого конкретного отчёта получена
и сохранена их историческая привязка. В интерфейсе теперь различаются:

- отчёт старше начала сохранения процессов (показана дата начала);
- агент присылает только текущий список без ID/времени исходного отчёта;
- список процессов от агента вообще не получен;
- метрики уже поступили, а отдельная отправка процессов ещё не завершилась;
- агент сообщил, что не смог прочитать процессы.

Исправлен локальный сборщик `serversstatus-host-monitor`: ранее его процессы
попадали только в latest_processes. Теперь отчёт и исторический сжатый список
сохраняются с явной привязкой в одной транзакции. Старые отсутствовавшие списки
восстановить нельзя; после restart сборщика новые снимки содержат процессы.
Для удалённого Linux нужен обновлённый агент с привязкой отчётов.

При отсутствующей отправке проверьте текущий блок «Процессы», журнал агента и
приём больших тел `/api/processes/*` на reverse proxy. Full-service upload
использует `/api/processes/{agent}/services` — существующее исключение Caddy
на 2MB для `/api/processes/*` подходит также для служб. При старом общем лимите
64KB используйте настройку из [PROCESSES.md](PROCESSES.md).

После обновления портала исторический список процессов сохраняется полностью
в рамках лимитов агента (до 10000 строк / примерно 1,9 Мб исходных данных),
а не только топ. Старые топ-архивы показываются с явной отметкой.
История процессов хранится вместе с отчётами по общей настройке (по умолчанию 186 дней).

Службы сохраняются сжатыми ревизиями при изменении инвентаризации. В снимке
используется последняя ревизия, полученная до времени отчёта, с указанием её
времени; текущие службы не подставляются в прошлое. Для нового архива служб
обновление агента не нужно, если он уже передаёт полный список.
Устаревшие ревизии чистятся по настроенному сроку (по умолчанию 186 дней); последняя ревизия до границы
сохраняется, чтобы описывать неизменившиеся службы в оставшихся снимках.
Агент с прежними текущими процессами без report_id требует обновления.
