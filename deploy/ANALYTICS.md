# Прогноз дисков, графики, события, суточная сводка и RDP

## Обновление Raspberry Pi

    cd /opt/ServersStatus
    sudo git pull --ff-only origin main
    sudo systemctl restart serversstatus

    sudo cp deploy/serversstatus-events.service deploy/serversstatus-events.timer /etc/systemd/system/
    sudo cp deploy/serversstatus-notify.service /etc/systemd/system/
    sudo systemctl daemon-reload
    sudo systemctl enable --now serversstatus-events.timer serversstatus-notify.timer
    sudo systemctl start serversstatus-events.service

Существующие файл Telegram с токеном и настройка SOCKS/Hysteria2 сохраняются.
Основной web unit менять не требуется. Новые таблицы создаются автоматически.
Если отдельные unit-файлы ранее меняли вручную, сохраните свои изменения перед
заменой. В notify service увеличен таймаут для очереди уведомлений/суточной сводки.

## Прогноз заполнения

Откройте карточку сервера: прогноз расположен под подробными показателями.
Используются часовые средние свободного места за последние 7 дней. Нужны минимум
12 часовых точек и 24 часа наблюдений. Изменение ёмкости тома обнуляет старый
сегмент анализа. При отсутствии устойчивого расхода, слабом тренде или слишком
редких измерениях панель не выдаёт выдуманный срок. При потере связи прогноз
помечается недоступным.

Это линейная оценка, а не гарантия даты отказа: очистка бэкапов, удаление файлов,
рост SQL и расширение томов меняют результат. Уже накопленная история пригодна,
обновление Windows только ради прогноза не требуется.

## Графики сети и дисковых операций

В карточке нажмите «Графики нагрузки» / «История нагрузки». Кроме CPU/RAM теперь
есть приём/передача сети, чтение/запись диска и IOPS. Выберите конкретные сетевой
интерфейс и дисковое устройство; выбор сохраняется при смене периода.
Шкала скорости автоматическая, а не 0–100%. Разрывы отчётов не заменяются нулями.
История использует уже полученные расширенные метрики. Снимки скорости собираются
примерно за секунду перед каждым отчётом; это не средняя скорость за всю минуту
и не измеренный полный объём переданного за сутки трафика.

## Журнал событий

Ссылка в шапке главной панели. Сохраняются начала проблем и восстановления:
связь, бэкапы, заполнение дисков от 85%, контролируемые службы; также изменения
настроек, регистрация/удаление/перевыпуск ключа, названия и блокировки входа.
Есть фильтры по ID агента/уровню и переход к старым событиям. Хранение — по настройке суперадминистратора в `/portal-settings` (по умолчанию 186 дней).
История начинается с установки новой версии, старые инциденты не выдумываются.

Отдельный таймер записывает переходы примерно раз в минуту даже при закрытой
панели и без настроенного Telegram. Повторные проверки одной проблемы не создают
одинаковые строки. Telegram теперь также уведомляет о службах и дисках;
сразу после обновления могут прийти уже существующие проблемы этих типов.

## Суточный отчёт Telegram

По умолчанию отправляется после 09:00 МСК в будни и после 12:00 в выходные
за предыдущий календарный день. Автоматические сообщения отправляются только
до 20:00 МСК.
Включает среднее/пиковое CPU, среднее RAM, число событий проблем за сутки и
текущее состояние связи, свободного места, бэкапов и служб. Суточные и текущие
показатели подписаны отдельно. Если за день данных нет — это явно указано.

При желании добавьте в существующий /etc/serversstatus-telegram.env:

    STATUS_DAILY_REPORT_ENABLED=1
    STATUS_DAILY_REPORT_HOUR=9

Час от 0 до 23, по Москве независимо от часового пояса Raspberry Pi. Для
отключения только сводки задайте ENABLED=0. Обычные тревоги продолжат работать.
Тестовая отправка прямо сейчас:

    cd /opt/ServersStatus
    sudo bash deploy/telegram-command.sh --daily-test

Тест не отмечает плановую сводку отправленной. Плановая очередь и прогресс
многочастного сообщения сохраняются в SQLite. При ошибке повторяются оставшиеся
части, учитывается retry_after. После запуска позже 09:00 отправится отчёт за
вчера, но пропущенные дни выключенного Raspberry Pi автоматически не создаются.
Как и обычный Telegram Bot API, доставка при потере ответа после принятия
сообщения не гарантирует строго однократную доставку.

## Windows: службы 1С/SQL и RDP-пользователи

Скачайте последнюю успешную сборку ServersStatus-Windows-x64 из GitHub Actions.
Запустите ServersStatusSetup.exe от администратора и нажмите «Обновить
установленный агент». Ключи и локальные настройки сохраняются.

Новый агент обнаруживает службы SQL Engine (MSSQLSERVER/MSSQL$...), SQL Server
Agent и 1С по имени/описанию службы и показывает их состояние. Автоматический
контроль включён по умолчанию; отключается отдельным флажком в настройках агента
в панели. Ручной список служб остаётся доступным. Старым EXE передаётся прежний
формат настроек, но автоматический поиск и RDP доступны только новой сборке.

В подробностях сервера появится «Пользователи RDP»:
- имя пользователя с доменом;
- ID сессии;
- подключённая или отключённая сохранённая сессия;
- число подключённых пользователей и активных сессий.

Используется WTS API Windows (через pywin32), а не разбор локализованного вывода
команд. Консольные сессии исключаются. Сбор чтением, без паролей пользователей
и без отключения сессий. При ошибке прав показывается «недоступно», а не ложный
пустой список. Вывод ограничен первыми 200 RDP-сессиями.
Служба обычно работает от LocalSystem; если изменяли её учётную запись,
проверьте право перечисления чужих сессий на RDP-сервере.

Когда добавите будущий сервер ТСД, зарегистрируйте агент в панели и установите
на нём новую сборку. Специально настраивать список имён не нужно.
RDP API и обнаружение служб проверены имитацией в тестах; реальный Windows
Server/RDP и перезагрузку необходимо проверить на вашем компьютере.

## Графики внутри снимка: пять минут до и после

В карточке исторического снимка графики CPU и RAM показывают окно от −5 до +5
минут относительно выбранного отчёта. Сам отчёт всегда в центре, отмечен золотой
пунктирной линией и выделенной точкой; верхние числа CPU/RAM остаются значениями
именно этого отчёта. Используются реальные соседние отчёты только этого агента,
не более 450 с каждой стороны. При отсутствии данных линия не продолжается
выдуманными значениями; у свежего снимка правая часть может быть пустой.
В подсказках RAM сохранён объём занятой/общей памяти. Точки можно открывать
в подробном графике по исходному report_id. Текущие карточки на главной по-прежнему
показывают последние пять минут, режим снимка не меняет их шкалу.

## Нагрузка логических процессоров

Агенты Windows/Linux передают `cpu_per_core`: значения по каждому логическому
процессору в порядке, возвращаемом psutil/ОС. Потоки SMT/Hyper-Threading учитываются
по отдельности. Физическое число ядер берётся из системной информации; привязка
потоков к физическим ядрам не выдумывается, особенно на гибридных CPU.
Общая и отдельные загрузки измеряются за тот же интервал около секунды без
дополнительного блокирующего ожидания; частота отчётов остаётся 10 секунд.

В карточке CPU нажмите «По ядрам · логические процессоры». Общий график
заменится сеткой мини-графиков — по одному на каждый логический процессор.
«Общая загрузка» возвращает исходный вид. Данные загружаются только при раскрытии, обновляются
раз в 10 секунд; раскрытие/выбранная страница/прокрутка сохраняются при обновлении
карточки. В интерфейсе сразу представлены все CPU, без пагинации.
Для большого числа процессоров сетка прокручивается внутри блока. Мини-график берёт
последний исходный отчёт в каждом 10-секундном интервале, чтобы не раздувать SVG.
Кнопка CPU N или точка открывает подробную историю этого CPU (до 900 исходных
отчётов без усреднения). Периоды без данных и смена числа CPU не заполняются нулями.

В снимке ядра берутся из выбранного report_id и рисуются в окне ±5 минут,
сам момент выделен. В старые снимки текущие значения не подставляются.
Сбор по ядрам начинается после обновления агентов; старые отчёты не восстановить.
Просмотр этих исторических графиков доступен администратору/суперадмину;
для роли текущего просмотра скрыт, прямой API тоже проверяет права.

Обновите портал на Raspi (`git pull`, restart serversstatus), после завершения
GitHub-сборок обновите Windows/Linux-агенты через «Обновить все агенты».
Для самой Raspi при установленном мониторинге дополнительно перезапустите
`sudo systemctl restart serversstatus-host-monitor`. Новых Python-зависимостей
нет. Версия локальной ИИ-модели и её ресурсные настройки не меняются.


## Температуры оборудования

В карточке сервера и в снимках есть сворачиваемый раздел «Температуры»:
имя датчика, устройство, компонент/источник, °C, сообщённые источником пределы,
время измерения (МСК). Число и набор зависят от оборудования. Отсутствующий
датчик/показание не заменяются нулём. Критические цвета используют только
переданные аппаратным источником high/critical; новых Telegram-оповещений нет.
Данные входят в исходные отчёты и сохраняются с прежней ретенцией.

Linux: стандартный psutil.sensors_temperatures / hwmon/sysfs. Показываются CPU
package/cores, NVMe/диски, GPU, DIMM, плата и прочие доступные каналы. Отдельные
ОЗУ/SATA/RAID датчики могут требовать аппаратной поддержки/драйвера; система
не устанавливает драйверы или SMART-утилиты и не включает скрытые датчики сама.

Windows: только чтение штатного ACPI-провайдера Windows —
MSAcpi_ThermalZoneTemperature в root\wmi. Встроенная библиотека LibreHardwareMonitor,
.NET-компонент, PawnIO, установщик и автоматическая установка драйверов удалены.
Внешние LibreHardwareMonitor/OpenHardwareMonitor WMI также больше не опрашиваются.
ACPI-зона не считается температурой CPU или памяти; при отсутствии датчика
показывается отсутствие данных. Значения переводятся из десятых кельвина в °C.
Фоновый опрос раз в 10 секунд, timeout 9 с, данные старше 120 с не выдаются как
текущие. Linux/Raspberry Pi продолжают чтение hwmon/sysfs.

Эта версия не устанавливает, не запускает, не останавливает и не удаляет PawnIO.
Уже установленный драйвер остаётся в системе: обновление агента не является
восстановлением пострадавшего Windows-сервера и не отключает старый драйвер.
Удаление/отключение на таких серверах проводится отдельно после проверки ОС.
Старые версии со встроенным компонентом не следует устанавливать или выбирать
для отката. Изменения исходников сами не перезапускают серверы. Применение
обновления агента перезапускает его службу и кратковременно прерывает мониторинг;
перезагрузка ОС для этого изменения не запрашивается и не выполняется.

В плотном режиме ядер внутри каждой ячейки оставлен только график: высота 24 px,
минимальная ширина 40 px, промежутки 2 px, без заголовков/процентов/двойной рамки.
Номер CPU и текущий процент доступны в подсказке при наведении и accessible name;
нажатие на любой мини-график открывает его подробную историю. Переключение обратно
на общую загрузку и выбранный режим при автообновлении сохраняются.

### Raspberry Pi — портал (raspi-portal)

Локальная служба serversstatus-host-monitor использует общий Linux-сборщик
температур, без LibreHardwareMonitor/PawnIO. Если он не вернул датчиков, доступное
показание `/sys/class/thermal/thermal_zone0/temp` добавляется в общий раздел
«Температуры» как SoC и сохраняется в отчётах/снимках. Старое значение в разделе
администрирования Raspberry Pi также сохраняется. Недоступный датчик не становится
нулём. После обновления исходников перезапустите **обе** службы:

```bash
sudo systemctl restart serversstatus serversstatus-host-monitor
```

Отдельно обновлять агент через Windows/Linux releases для raspi-portal не нужно:
он запускается из того же репозитория /opt/ServersStatus.
