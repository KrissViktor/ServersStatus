# Список процессов и подробности RDP

## Панель на Raspberry Pi

    cd /opt/ServersStatus
    sudo git pull --ff-only origin main
    sudo systemctl restart serversstatus
    sudo systemctl try-restart serversstatus-host-monitor
    sudo systemctl try-restart serversstatus-bot

На странице конкретного сервера появится раздел «Процессы»:
- первые 10 по CPU, кнопка «Показать все» / «Свернуть до 10»;
- сортировка по CPU, памяти, PID, имени и пользователю в обе стороны;
- PID, имя, владелец, CPU, память RSS и состояние;
- обновление каждые 10 секунд с сохранением сортировки и раскрытия;
- при потере связи явно указывается возраст последнего списка.

CPU нормализован на общую мощность всех логических процессоров: процесс,
полностью загрузивший одно из четырёх ядер, показывает около 25%.
Новые процессы, появившиеся между началом и концом измерения, получают «—»
для CPU. Недоступные по правам сведения не подменяются нулём.
На Windows System Idle Process (PID 0) не считается потребителем CPU.

Полный список хранится только в latest_processes — один последний снимок на
сервер. История CPU/ОЗУ/сети/дисков продолжает записываться каждые 10 секунд
с прежним сроком хранения. После обновления агента к исходным отчётам
добавляются сжатые исторические топ-10 по CPU и топ-10 по памяти (до 20
процессов без дубликатов) со сроком 186 дней. Полные многотысячные списки
в историю не копируются; объём базы увеличивается на компактные топы.
Снимок связан с конкретным отчётом по ID и времени получения. Старые агенты
продолжают отправлять последний список, но без исторической привязки.
При необычно больших списках действует предел 10 000 строк и размер снимка
около 1,9 Мб; сокращение отмечается в интерфейсе. Командные строки процессов
не собираются.

## Caddy: разрешить передачу большого списка

Для большого списка процессов нужен отдельный лимит тела запроса.
На Raspberry Pi сохраните копию конфигурации:

    sudo cp -a /etc/caddy/Caddyfile /etc/caddy/Caddyfile.before-processes
    sudo nano /etc/caddy/Caddyfile

Внутри существующего блока panel.vikserver.ru замените:

    request_body {
        max_size 64KB
    }

на:

    @processes path /api/processes/*
    request_body @processes {
        max_size 2MB
    }
    @standard not path /api/processes/*
    request_body @standard {
        max_size 64KB
    }

Сохраните домен, reverse_proxy, настройки IP, таймауты и остальные правила.
Тот же пример обновлён в deploy/Caddyfile. Затем:

    sudo caddy validate --config /etc/caddy/Caddyfile
    sudo systemctl reload caddy

Приложение тоже ограничивает размер, проверяет ключ агента и формат каждой
строки. Просмотр списка доступен только после входа в панель. Если дополнительный
запрос отклонён, основной отчёт сервера и применение настроек продолжают работать.

## Обновить агентов

Новые данные появятся после обновления агента. Используйте раздел «Обновления»
и пакеты успешной новой сборки GitHub Actions, как описано в deploy/UPDATES.md.
Если первичная поддержка удалённого обновления ещё не установлена, сначала
выполните ручной шаг из той же инструкции. Windows-артефакт:
ServersStatus-Windows-x64; Linux: ServersStatus-Linux-Python311.
Зависимости Linux не изменились, совместимое обновление можно назначить из панели.
Монитор Raspberry Pi получает сбор процессов вместе с обновлением кода портала.

## Подробности RDP

На Windows показываются пользователь, ID и состояние сеанса, время входа (МСК),
длительность, простой, имя компьютера и IPv4 клиента. Эти же подробности
добавлены в ответ кнопки RDP в Telegram. Активные сеансы отмечены зелёным,
отключённые — красным. Отключённый сеанс может продолжать содержать работающие
приложения пользователя.

Время читается из Windows WTSINFO, а не вычисляется на основании первого
появления пользователя в панели. Простой отражает последний ввод, который
предоставила Windows; для отключённых сеансов он не является длительностью
отключения. IP клиента иногда отсутствует, может быть адресом промежуточного
узла и не гарантирует исходный IP при работе через шлюз/NAT. Если Windows не
предоставляет поле, показывается «—». Linux RDP-сеансы этим способом не собирает.
Старые агенты продолжают отправлять прежние отчёты; до обновления новые поля
будут пустыми. Управление процессами и RDP-сеансами в этом изменении не добавлено.
