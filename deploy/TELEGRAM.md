# Telegram-уведомления на Raspberry Pi

Windows-агенты обновлять не требуется. Уведомления отправляются только в указанный
вами чат. Используйте отдельного бота ServersStatus, без webhook и других обработчиков.

## 1. Обновить проект

```bash
cd /opt/ServersStatus
sudo git pull --ff-only origin main
sudo systemctl restart serversstatus
```

## 2. Создать бота

В Telegram откройте **@BotFather**, отправьте `/newbot`, задайте название и username.
Сохраните полученный токен. Откройте своего бота и отправьте ему `/start`.
Для группы добавьте бота в группу и отправьте команду `/start@имя_бота`.
Токен даёт доступ к боту: не присылайте его в чат и не коммитьте в Git.

## 3. Сохранить настройки на Raspberry Pi

```bash
sudo touch /etc/serversstatus-telegram.env
sudo chmod 600 /etc/serversstatus-telegram.env
sudo nano /etc/serversstatus-telegram.env
```

Содержимое (вставьте свой токен вместо примера):

```dotenv
STATUS_TELEGRAM_TOKEN=ВАШ_ТОКЕН_БОТА
STATUS_TELEGRAM_CHAT_ID=
```

Сохраните файл. Для определения ID чата выполните:

```bash
cd /opt/ServersStatus
sudo bash deploy/telegram-command.sh --discover-chat
```

Команда выводит ID и название найденных чатов, не токен. Выберите нужный ID,
снова откройте env-файл и заполните `STATUS_TELEGRAM_CHAT_ID`. У группы ID может
быть отрицательным — сохраните знак минус. Если список пуст, отправьте боту `/start`
и повторите. При активном webhook или другом потребителе getUpdates этот способ
может не работать: используйте отдельного бота. Не указывайте токен в адресной
строке браузера, аргументах команд или переписке.

## 4. Проверить отправку

```bash
sudo bash deploy/telegram-command.sh --test
```

Должно прийти тестовое сообщение. При ошибке проверьте токен, ID, что пользователь
запустил бота и не заблокировал его, и что Raspberry Pi имеет доступ по HTTPS к
`api.telegram.org:443`. Код не обходит сетевые ограничения и не отключает TLS.

## 5. Включить автоматическую проверку

```bash
sudo cp deploy/serversstatus-notify.service deploy/serversstatus-notify.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now serversstatus-notify.timer
sudo systemctl start serversstatus-notify.service
sudo systemctl list-timers serversstatus-notify.timer
```

Задача проверяет состояние примерно раз в минуту, даже при закрытой панели.
На первом запуске отправятся текущие проблемы (до 20 сообщений за один проход).

Проверить журнал:

```bash
sudo journalctl -u serversstatus-notify.service -n 30 --no-pager
```

Отключить уведомления:

```bash
sudo systemctl disable --now serversstatus-notify.timer
```

После изменения env-файла следующий запуск задачи прочитает новые значения.
При смене чата старые инциденты автоматически повторно не отправляются; проверяйте
новый чат через `--test`.

## Какие события отправляются

- Нет контакта с ранее подключённым агентом 3 минуты и последующее восстановление.
- Проблемы бэкапов по тем же правилам, что в панели: возраст, размер, отсутствие
  файлов, ошибка доступа, дата из будущего.
- Восстановление бэкапа после нового подтверждённого отчёта. Файл в состоянии
  ожидания стабильности не считается подтверждением восстановления.

Одна проблема одного правила — одно сообщение до восстановления, даже если
возраст копии растёт. Новая причина в том же проблемном правиле не создаёт нового
письма до восстановления. При потере связи старые проблемы бэкапов удерживаются,
а не объявляются восстановленными. Удаление агента/правила не считается восстановлением.
Новые агенты без первого отчёта не создают уведомления о недоступности.

Состояние отправки хранится в таблице telegram_state той же SQLite; при перезапуске
оно сохраняется. Ошибки доставки повторяются, учитывается Telegram retry_after.
Текст в журнале не содержит токен. Стандартный Telegram Bot API не обеспечивает
строго однократную доставку: при потере ответа после принятия сообщения или аварии
между отправкой и записью состояния возможен повтор. Если отключится сам Raspberry
Pi или его интернет, он не сможет сообщить об этом — нужен внешний мониторинг.
